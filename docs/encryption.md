# Encryption

Recruvault uses envelope encryption. Each field or document has its own data key. New data keys are wrapped by a customer key for that organisation or job seeker, or sealed to that owner's public key when the writer is a secure-link responder.

This is not zero-knowledge.

| Threat | Result |
| --- | --- |
| Database copy without session cookies or API keys | New envelopes stay unreadable. Legacy envelopes still open with `LOCAL_KEK`. |
| Object store copy | Document objects are ciphertext. The original filename is not in the object key. The database still stores the filename, content type, size, and checksum as metadata. Legacy plaintext objects remain until the migration below moves them. |
| Unlocked session or stolen API key | The server can decrypt that owner's records until the session ends or the key is revoked. |
| Password reset | Does not replace or reveal the customer key. The next session must enter it again. |
| Operator with `LOCAL_KEK` | Can read legacy rows, legacy plaintext objects not yet migrated, and organisation JDs and NDAs, which are render-delegated so a secure link can display them. Candidate evidence, wallet values, and wallet files never get that delegation. |
| Lost customer key | Profiles, documents, and submissions protected by that key stay ciphertext. Password reset, support, and `LOCAL_KEK` cannot reconstruct it. There is no replacement key. |
| Lost backup key and `LOCAL_KEK` | R2 archives cannot be opened. The live workspace is unaffected. A saved backup key, or `LOCAL_KEK` plus the database, can still open them. |
| Backup taken before deletion | Can still contain ciphertext and the wrapped data keys. Destroying the data key in the live database does not erase that backup. |

Sharing with a recruiter copies the submission into an envelope sealed to the organisation. Revoking a wallet share does not remove a submission that was already received.

`BOOTSTRAP_TOKEN` is the first-owner capability. It is separate from the customer key and from `BETTER_AUTH_SECRET`. See [First-owner bootstrap](#first-owner-bootstrap).

API keys expire, carry explicit scopes, and hold a wrap of the customer key created while the vault was unlocked. `legacy:full` is only the migration scope for keys that already existed. New keys cannot use it. A reporting key cannot create roles, upload JDs, send invitations, list submissions, or change a profile. Legacy keys are not upgraded; they must be replaced.

## Customer keys

Each organisation and each job seeker enrols one customer key before using a workspace. Three forms are accepted:

- **Generated**: 256 random bits from the browser's CSPRNG, shown once for the owner to save.
- **Imported**: a 256-bit base64url key. Keys with fewer than 16 distinct bytes, a repeating pattern of up to 16 bytes, or a constant step (`00 01 02 …`) are rejected as not random.
- **Passphrase**: at least 12 characters, derived with scrypt. New vaults use parameter version 2 (`N=2^17, r=8, p=1`). The 16-byte salt is generated by the server. The salt and parameters are stored with the vault, and unlocking always uses the stored values, so version 1 vaults (`N=2^14`) keep working. Parameters outside reviewed bounds are refused, so an edited row cannot weaken or abuse the derivation.

Enrolment needs the key twice and an explicit backup acknowledgement. The database stores only an HMAC verifier bound to the owner, the owner's X25519 public key, the private key wrapped by the customer key, the KDF salt and parameters, the key version, and its status (`active`, `pending`, `retired`). The raw key is never stored, logged, audited, or put in a URL or browser storage. Concurrent enrolments are serialised; the loser is told a key already exists.

Every data-key envelope authenticates `owner type | owner id | data key id | purpose | key version`. The reader recomputes this context from the row's columns instead of trusting a stored copy, so moving a row to another owner, version, or purpose makes it fail to open. Secure-link drafts bind the link id the same way.

### Enforcement

| Requirement | Applies to |
| --- | --- |
| Enrolled and unlocked in this session | Dashboard and seeker pages; creating roles and requests; sending invitations; sharing; changing members, roles, settings, sending domain, match and alert settings; saved roles and discovery profile; uploads; API key creation; backup settings |
| Enrolled | Revoking links and shares; deleting templates, submissions, wallet items, and documents; removing a member |
| Neither | Account erasure, which stays available to someone who has lost their key (it requires typing `DELETE`) |

REST and MCP callers use the same rules through API keys that carry a delegation of the customer key (see below). A secure-link draft is refused when the requesting organisation has not enrolled. Organisation creation, first-owner setup, and job-seeker onboarding all include the key step.

### Unlock behaviour

| Event | Result |
| --- | --- |
| Refresh or new tab | Stays unlocked. The key is wrapped by a per-browser cookie secret and stored against the session. |
| Browser restart | Locked. The cookie secret is a session cookie. |
| Logout | Locked. The session row and its unlock rows are deleted. A copied cookie no longer works. |
| Session expiry | Locked. Unlock rows expire with the session. |
| New device or browser | Locked until the key is entered there. |
| Password reset | Every session is revoked, so every unlock is gone. The customer key does not change and is still required. A reset never decrypts or replaces it. |
| Magic-link or passkey sign-in | Starts a new, locked session. |
| Key rotation completes | Every other session and every API key bound to the old key is locked out. Unlock again with the new key and issue new API keys. |

Unlock attempts are rate limited per user, and failures are audited without key material.

### Rotation

Rotation rewraps each data key; it never rewrites field ciphertext or document bytes. It needs the owner role, a sign-in from the last 15 minutes, the current key, and the new key, and it is rate limited and audited (`vault.rotation_started`, `_completed`, `_failed`, `_cancelled`).

1. In one transaction the server creates the pending key version, a rotation record, and a *bridge*: the new key wrapped by the current key.
2. Batches of data keys are rewrapped under the new version. Each new envelope is decrypted and compared with the original key before it is written. Each batch commits on its own; a crash rolls back only that batch.
3. While the rotation is pending, sessions and API keys holding the current key keep reading moved records through the bridge. New records keep using the current version and are picked up by later batches.
4. The switch takes a row lock on the active key and recounts. Writers take a share lock on the same row when they insert a data key, so a write either lands before the recount (and is rotated) or sees the switch and fails with a retryable error. No record can be left on a retired version.
5. On switch the old version is retired and its wrapped private key is deleted, the bridge is deleted, other sessions' unlocks are removed, and API keys bound to the old key are revoked.

An interrupted rotation resumes when the same pair is submitted again. A different new key is refused while one is pending. **Cancel** needs only the current key: it opens the bridge, moves every record back, and deletes the pending version. This is the rollback path if the new key is lost before the switch. After the switch there is no rollback; the old key opens only backups taken before it.

Rotation does not revoke plaintext or keys an attacker already copied. See the compromise procedure in [operations](operations.md#suspected-key-compromise).

### Legacy field migration

Field keys written before customer keys are wrapped by `LOCAL_KEK`. When an owner unlocks or enrols, and from **Migrate older records** on the rotation page, the server rewraps that owner's legacy field keys under the customer key in place: wallet values for a job seeker, submitted answers for an organisation. Each batch is verified and committed separately and the run can repeat safely. The data key and ciphertext do not change, so a record is readable throughout, through `LOCAL_KEK` before its batch commits and through the customer key after. Open secure-link drafts stay on `LOCAL_KEK` because the responder still needs them. `LOCAL_KEK` itself is never changed. Document keys move with the document migration below.

### Recovery guarantees

There is no operator-held recovery key. Recruvault cannot reset, reveal, or re-derive a customer key. If every copy of it is lost, the records it protects stay ciphertext. Password reset, support, `LOCAL_KEK`, and backups cannot change that. The one exception is the rotation bridge: during a pending rotation, the current key can still cancel and recover the new one.

## First-owner bootstrap

Setup is open only until the `platform_bootstrap` row is consumed. That row, not "some owner exists", is the source of truth, and every app instance checks it. It never reverts.

1. The visitor creates an account at `/setup` (or signs in to one) through the normal BetterAuth flow. It is created as a job-seeker account even when recruiter self-registration is off; clients cannot choose `accountType` on sign-up or through `update-user`.
2. The emailed verification link returns to `/setup`. Setup never marks an address verified itself.
3. The verified account submits the organisation name, `BOOTSTRAP_TOKEN`, and a new customer key. Under an advisory lock, in one transaction, the server checks the token in constant time, makes the account an organisation account, creates the organisation, owner membership, and vault key, and consumes the bootstrap row. Concurrent claims produce exactly one owner.

The token is accepted only in the Server Action body, never in a URL. Attempts are rate limited per client address and across the whole deployment. Failures are audited without the token. Ordinary organisation creation is refused until bootstrap completes. If an organisation exists without an owner (an interrupted pre-bootstrap install), only `BOOTSTRAP_RECOVERY_TOKEN` can adopt it, and the claimant must present that organisation's existing customer key.

## Documents

Every upload is scanned in memory, then encrypted under a new per-document data key before it reaches S3 or MinIO. The object key is opaque (`org/<owner>/<uuid>` or `wallet/<owner>/<uuid>`) and the stored content type is `application/octet-stream`.

- The envelope is AES-256-GCM. Envelope v2 authenticates the owner type, owner id, document id, document kind (`jd`, `nda`, `evidence`, `resume`, ...), and the version. v1 envelopes, which bound the literal purpose `bytes`, still open.
- Recruiter uploads wrap the key with the organisation key (signed-in session) or seal it to the organisation's public key (API and secure-link uploads). Wallet uploads wrap it with the job seeker's key.
- Only organisation JDs and NDAs also carry a `LOCAL_KEK` render wrap, so a verified secure-link responder can view them. Candidate evidence and wallet files never do.
- Every view, download, and watermark render authorises first, then decrypts. A locked vault returns 409, a shredded key or removed object returns 410, and any authentication failure (tampered bytes, swapped document id or kind, another owner's key) returns 500 without serving bytes.
- Deleting a document shreds every wrap of its key, including the render wrap, in the transaction that queues the object for deletion. The object is unreadable from that commit, even while deletion retries.

### Legacy plaintext migration

Objects written before envelopes are read as plaintext until they migrate. The `migrate-legacy-documents` job runs every 10 minutes in batches of 25. For each document it:

1. takes a lease on its `document_migrations` row, discarding an expired earlier attempt (key shredded, object queued);
2. checks the original against the stored checksum and size;
3. seals a new data key to the owner's public key (no unlock needed), writes the ciphertext under a new key, reads it back, decrypts it, and compares checksum and size;
4. switches the row, marks the migration done, and queues the original for deletion, in one transaction.

The original stays referenced and readable until step 4 commits. A failure leaves the document on its original and is retried; after five failed attempts the migration is marked `failed` and the original is kept. Owners without an enrolled key are counted as awaiting enrollment. Pending scans are left to the scanner. Each run logs counts only: before, migrated, awaiting enrollment, busy, failed, remaining.
